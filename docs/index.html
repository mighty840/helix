Helix

Programs encoded as DNA sequences. Compile your algorithm to ACGT, decode it back and execute it. Storage and errors are simulated in software.

6 crates32 opcodes Reed-Solomon ECCbio-safety linter168 tests

What is Helix?

§ 1.0

Helix is a system for encoding executable algorithms as synthetic DNA sequences. Programs are compiled to an ACGT nucleotide string, decoded back, and executed on a software virtual machine.

The design goal is to store fundamental algorithms (sorting, searching, arithmetic) in synthetic DNA. Everything in Helix runs in software: no sequence has been synthesized, stored or sequenced, and storage errors are injected by helix-sim at rates you choose.

Helix is not biological computation. It uses DNA as a storage medium, the same way you'd use tape or flash.

Encode & Run

§ 2.3
R7 holds the
return value
by convention
src/main.rs 
use helix_asm::Assembler;
use helix_ecc::EccConfig;
use helix_vm::{Cpu, Memory, ProgramLoader};

fn main() -> anyhow::Result<()> {
    let src = r#"
        .program "add_example"
        .version 1
        .text
        .entry main
        main:
          IMML R1, 21
          IMML R2, 21
          ADD  R7, R1, R2
          HALT
    "#;

    // SYNC markers + Reed-Solomon + three copies (TMR)
    let cfg = EccConfig::default();
    // assemble: source -> DNA string, with bio-safety codon swaps
    let out = Assembler::new(cfg, true).assemble(src)?;
    println!("{} nt", out.dna.len());
    // load: DNA string -> ECC decode -> instructions
    let prog = ProgramLoader::new(cfg).from_dna_string(&out.dna)?;
    let mut cpu = Cpu::new(Memory::new());
    cpu.run(&prog.instructions)?;
    println!("R7 = {}", cpu.regs[7]); // 42
    Ok(())
}

Full Round-Trip (with ECC)

§ 2.4
src/bin/roundtrip.rs 
use helix_bio::SequenceOptimizer;
use helix_ecc::{EccConfig, EccDecoder, EccEncoder};
use helix_isa::{encode_instruction, Codon, Instruction, Register::*};
use helix_vm::{Cpu, Memory, ProgramLoader};

fn main() -> anyhow::Result<()> {
    let program = [
        Instruction::Imml(R1, 21),
        Instruction::Imml(R2, 21),
        Instruction::Add(R7, R1, R2),
        Instruction::Halt,
    ];
    let mut codons: Vec<Codon> = program.iter().flat_map(encode_instruction).collect();
    let report = SequenceOptimizer::default().optimize(&mut codons);
    println!("bio violations left: {}", report.violations.len());

    let cfg = EccConfig::default();
    let mut stored = EccEncoder::new(cfg).encode(&codons);
    // simulated damage: change one codon in the first copy
    stored[5] = Codon::new(stored[5].value() ^ 0b11);

    let recovered = EccDecoder::new(cfg).decode(&stored)?;
    let prog = ProgramLoader::from_raw_codons(&recovered)?;
    let mut cpu = Cpu::new(Memory::new());
    cpu.run(&prog.instructions)?;
    println!("R7 = {}", cpu.regs[7]); // 42
    Ok(())
}
Both programs print R7 = 42. The second changes one codon of the first copy before decoding; the three-copy vote repairs it. Everything here runs in software.

ISA Overview
ISA Reference · §4

Design Goals

§ 4.1

The Helix ISA is optimised for DNA storage, not speed. Every design decision trades execution efficiency for storage robustness:

  • Fixed-width instructions — 4 codons each, so block boundaries are predictable
  • Small opcode space — 32 opcodes (5 bits); leaves room for bio-safe codon selection
  • No memory-mapped I/O — LOAD/STORE address a small scratch RAM only
  • Relative branches — signed 8-bit offsets; no absolute addresses in DNA

Load a 16-bit Immediate

§ 6.3

IMML/IMMH write 8 bits at a time. To load a full 16-bit constant into R1:

load_1000.hx snippet 
  IMML R1, 232    ; R1[7:0]  = 0xE8  (1000 & 0xFF)
  IMMH R1, 3      ; R1[15:8] = 0x03  (1000 >> 8)
  ; R1 = 0x03E8 = 1000
Initialise registers with IMML only when the value fits in 8 bits. Use the IMMH+IMML pair for anything ≥ 256.
Reed-Solomon ECC
Error Correction · §7

RS(10, 8)

§ 7.1
corrects up to
1 symbol error
per block
(t = 1)

Helix uses a Reed-Solomon code over GF(2⁶) with parameters RS(10, 8): each block contains 8 data symbols and 2 parity symbols, producing 10-symbol codewords. One symbol = one codon value (6 bits).

Only the opcode codons (codon 0 of each instruction) are RS-protected per block of 8 instructions. Operand corruption beyond single-symbol correction falls to TMR.

Block Structure

§ 7.2
encoded block layout 
[ SYNC (4 codons) ]
[ instr₀ (4 codons) ]  ← codon₀ = opcode symbol 0
[ instr₁ (4 codons) ]  ← codon₀ = opcode symbol 1
  …
[ instr₇ (4 codons) ]  ← codon₀ = opcode symbol 7
[ ECCP, 0, parity₀, parity₁ ]  ← 2 RS parity symbols
= 10 instructions = 40 codons = 120 nt per block
The SYNC marker (4 known codons) marks where each block starts. The decoder searches for it at codon-aligned positions only, so a single inserted or deleted nucleotide is not re-framed in v0.1.x.

API

§ 7.3
ecc usage

// vote, find SYNC, correct one opcode codon per block

Triple Modular Redundancy
Error Correction · §8

How TMR Works

§ 8.1

TMR stores three copies of the encoded sequence back to back and takes a majority vote per codon at decode time. If two copies agree, the third is considered corrupt and the majority value wins.

The decoder splits the stream into thirds by length, so no separator is needed. (v0.1.0 placed a TGA codon between copies, but that value can also occur inside instructions; v0.1.1 still reads the v0.1.0 layout.) A stream whose length cannot be split this way, for example after an inserted or deleted codon, is rejected.

TMR is the outer layer of ECC. It repairs damage confined to one of the three copies, including a burst that wipes out a whole RS block, and it is the only layer that protects operand codons.

TMR triples the length of the stored sequence.

Voting Logic

§ 8.2
majority vote (conceptual) 
// For each codon position i:
let a = copy_a[i];
let b = copy_b[i];
let c = copy_c[i];
let voted =
    if a == b { a }
    else if a == c { a }
    else if b == c { b }
    else { a }  // no majority: copy A wins;

When to use TMR

§ 8.3

TMR is on by default (EccConfig::default()). Turn it off with tmr: false or --no-tmr for one copy: a third of the length, with only Reed-Solomon protecting opcode codons and nothing protecting operands.

Measured with helix-sim on gcd.hx, 200 runs, simulated substitutions only at 1%: 98.3% of instructions recovered with TMR, 73.9% without.

Why Constraints?

§ 9.1

Some sequence patterns are known to be hard to synthesize or sequence. Helix checks four categories of constraints in software before output. They have not been tested against a synthesizer.

Constraint Rules

Bio Optimizer
Bio Safety · §10

Codon Degeneracy

§ 10.1

The 6-bit codon space has 64 values, but Helix only uses values 0–31 for opcodes and 0–7 for registers. This leaves slack that the optimizer uses to substitute bio-problematic codons with synonymous alternatives that encode the same value but produce better GC content or break homopolymer runs.

Optimization Strategy

§ 10.2
  • Passes — up to 5 (SequenceOptimizer::default()); each pass lints the whole sequence
  • One swap per pass — for the first violation it can act on, it swaps the opcode codon of the instruction at that position, or of one of the two instructions before it, to its synonym
  • Scope — only opcodes 0x00 to 0x0F have a synonym (opcode + 32); operand codons never change, and SYNC, parity and TMR copies are added after this step
The optimizer rewrites opcode codons to their synonyms (opcodes 0x00 to 0x0F have one each) and reports the violations that remain.

Assembler
Toolchain · §11 — helix-asm

Pipeline

§ 11.1

The assembler transforms .hx source text into a DNA string:

  • Parse (helix_asm::parser) — tokenise and produce a SourceProgram with unresolved label refs
  • Resolve (helix_asm::resolver) — compute branch offsets, produce ResolvedProgram
  • Emit (helix_asm::emitter) — prepend a loader prologue when the program has a .data section or a non-zero .entry (it stores each data word at addresses 0, 1, 2, … through R6/R7, resets them, and jumps to the entry), encode each Instruction to 4 Codons, apply bio swaps, then ECC, and return AssemblyOutput

API

§ 11.2
assembler API 
use helix_asm::{Assembler, AssemblyOutput};
use helix_ecc::EccConfig;

let out: AssemblyOutput = Assembler::new(EccConfig::default(), true)
    .assemble(source_str)?;

// out.prologue_len : usize            loader instructions in front (.data, .entry)
// out.program      : ResolvedProgram  instructions, data, entry
// out.bio_swaps, out.bio_violations : usize

Virtual Machine
Toolchain · §12 — helix-vm

Execution Model

§ 12.1

The VM is a simple register machine: 8 × 16-bit registers, a program counter, a flags register (zero, negative, carry), and a RAM of 1024 × 16-bit words.

Execution is deterministic and synchronous — no threads, no I/O, no side effects. The same instructions always produce the same result. The CLI prints a per-instruction trace with helix-vm --trace.

API

§ 12.2
vm usage 
use helix_ecc::EccConfig;
use helix_vm::{Cpu, Memory, ProgramLoader};

let prog = ProgramLoader::new(EccConfig::default()).from_dna_string(&dna)?;
let mut cpu = Cpu::new(Memory::new());
let executed = cpu.run(&prog.instructions)?; // runs until HALT

println!("{executed} instructions");
println!("R1 = {}, R7 = {}", cpu.regs[1], cpu.regs[7]);

Simulator
Toolchain · §13 — helix-sim

What is helix-sim?

§ 13.1

helix-sim is a chaos / fault-injection harness. It simulates the DNA storage medium by randomly mutating a DnaSequence according to a configurable error model, decodes it, and counts how many decoded instructions equal the originals. It does not execute the program.

Error Injection Modes

§ 13.2
ModeDescription
CompositeIndependent substitution, deletion and insertion rates per nucleotide (--sub-rate, --del-rate, --ins-rate). Deletions and insertions shift the frame, which v0.1.x does not recover from.
BurstErrors concentrated in one random region (--burst, --burst-frac), simulating localized damage.

API

§ 13.3
simulator usage 
use helix_ecc::EccConfig;
use helix_sim::metrics::simulate;
use helix_sim::InjectionConfig;

// 1% substitutions, no deletions or insertions, seed 42
let inject = InjectionConfig::composite(0.01, 0.0, 0.0, 42);
let report = simulate(&dna, &original_instrs, inject, EccConfig::default());
// compares decoded instructions with the originals (does not execute)
println!("{:.1}% recovered", report.recovery_rate() * 100.0);
The rates are simulation parameters, not measured DNA error rates. Use --runs N to average over seeds (run n uses seed + n), e.g. helix-sim gcd.dna --sub-rate 0.01 --del-rate 0 --ins-rate 0 --runs 200.

GCD (Euclidean)

§ 14.3
gcd.hx 
; Euclidean GCD — compute GCD(a, b).
; Result: R1 = GCD(48, 18) = 6
;
; Algorithm: while b != 0: (a, b) = (b, a mod b)

"ck">.program "gcd"
"ck">.version 1
"ck">.text
"ck">.entry main

main:
    IMML R1, 48         ; a = 48
    IMML R2, 18         ; b = 18

    BEQ  done           ; yes → done, R1 holds GCD

    ADD  R1, R2, R0     ; a = b
    ADD  R2, R3, R0     ; b = a mod b
    JMP  loop

done:
    ; R1 = GCD(48, 18) = 6
    HALT
Quantized Values
Examples · §15 — one codon per 6-bit number

Concept

§ 15.1

A codon holds 6 bits, a number from 0 to 63. A list of numbers quantized to 64 levels can therefore be stored at one codon, three nucleotides, per number, with a rounding error of at most half a step.

The demo helix-vm/examples/weights.rs does this for 20 example values in [-0.890, 0.930]. It stores raw codons only: no SYNC, Reed-Solomon or TMR.

Quantisation

§ 15.2

With step = (max − min) / 63, each value w maps to q = round((w − min) / step), stored as the codon with value q, and is read back as min + q × step. For the demo's values the step is 0.02889, so the largest possible error is 0.01444.

Run

§ 15.3
cargo run --example weights --manifest-path helix-vm/Cargo.toml (excerpt) 
20 weights × 3 nt/codon = 60 nucleotides  (3.0 nt/weight)
MSE:      0.0000629
Max err:  0.01333  (theoretical max: 0.01444)
The 60 nucleotides hold 120 bits, the same as 15 bytes: 2 bits per nucleotide.
