Helix

Programs encoded as DNA sequences. Compile your algorithm to ACGT, decode it back and execute it. Storage and errors are simulated in software.

6 crates32 opcodes Reed-Solomon ECCbio-safe output159 tests

What is Helix?

§ 1.0

Helix is a system for encoding executable algorithms as synthetic DNA sequences. Programs are compiled to an ACGT nucleotide string, decoded back, and executed on a software virtual machine.

The design goal is to store fundamental algorithms (sorting, searching, arithmetic) in synthetic DNA. Everything in v0.1.0 runs in software: no sequence has been synthesized, stored or sequenced, and storage errors are injected by helix-sim at rates you choose.

Helix is not biological computation. It uses DNA as a storage medium, the same way you'd use tape or flash.

use helix_asm::Assembler;
use helix_vm::{Cpu, ProgramLoader};

fn main() {
    let src = r#"
        .program "add_example"
        .version 1
        .text
        .entry main

}

ISA Overview
ISA Reference · §4

Design Goals

§ 4.1

The Helix ISA is optimised for DNA storage, not speed. Every design decision trades execution efficiency for storage robustness:

  • Fixed-width instructions — 4 codons each, so block boundaries are predictable
  • Small opcode space — 32 opcodes (5 bits); leaves room for bio-safe codon selection
  • No memory-mapped I/O — LOAD/STORE address a small scratch RAM only
  • Relative branches — signed 8-bit offsets; no absolute addresses in DNA

Codon Encoding

§ 4.3

A codon is 3 DNA bases. Each base encodes 2 bits: A=00, C=01, G=10, T=11. So a codon GCA = 10 01 00 = 36.

Load a 16-bit Immediate

§ 6.3

IMML/IMMH write 8 bits at a time. To load a full 16-bit constant into R1:

load_1000.hx snippet 
  IMML R1, 232    ; R1[7:0]  = 0xE8  (1000 & 0xFF)
  IMMH R1, 3      ; R1[15:8] = 0x03  (1000 >> 8)
  ; R1 = 0x03E8 = 1000
Initialise registers with IMML only when the value fits in 8 bits. Use the IMMH+IMML pair for anything ≥ 256.
Reed-Solomon ECC
Error Correction · §7

RS(10, 8)

§ 7.1
corrects up to
1 symbol error
per block
(t = 1)

Helix uses a Reed-Solomon code over GF(2⁶) with parameters RS(10, 8): each block contains 8 data symbols and 2 parity symbols, producing 10-symbol codewords. One symbol = one codon value (6 bits).

Only the opcode codons (codon 0 of each instruction) are RS-protected per block of 8 instructions. Operand corruption beyond single-symbol correction falls to TMR.

Block Structure

§ 7.2
encoded block layout 
[ SYNC (4 codons) ]
[ instr₀ (4 codons) ]  ← codon₀ = opcode symbol 0
[ instr₁ (4 codons) ]  ← codon₀ = opcode symbol 1
  …
[ instr₇ (4 codons) ]  ← codon₀ = opcode symbol 7
[ ECCP parity₀ parity₁ padding ]  ← 2 RS parity symbols
The SYNC marker (4 known codons) allows the decoder to resync after frame loss — the most common error in long-term DNA storage.

API

§ 7.3
ecc usage 
use helix_ecc::{EccConfig, EccEncoder, EccDecoder};

// decode + correct DnaSequence → Vec<Codon>

Triple Modular Redundancy
Error Correction · §8

How TMR Works

§ 8.1

TMR stores three copies of the encoded DNA sequence and takes a majority vote at decode time. If two copies agree, the third is considered corrupt and the majority value wins.

TMR is the outer layer of ECC — it handles burst errors that span an entire RS block, which RS alone cannot correct.

TMR triples the length of the stored sequence.

Voting Logic

§ 8.2
majority vote (conceptual) 
// For each codon position i:
let a = copy_a[i];
let b = copy_b[i];
let c = copy_c[i];
let voted =
    if a == b { a }
    else if a == c { a }
    else if b == c { b }
    else { /* unresolvable — flag EccError */ };

When to use TMR

§ 8.3

TMR is optional and configured via EccConfig. Enable it for:

  • Expected long storage durations (> 100 years)
  • Environments with high radiation or oxidative stress
  • Critical algorithms where retrieval failure is unacceptable
Bio Safety Constraints
Bio Safety · §9

Why Constraints?

§ 9.1

Some sequence patterns are known to be hard to synthesize or sequence. Helix checks four categories of constraints in software before output. They have not been tested against a synthesizer.

Constraint Rules

§ 9.2
RuleLimitReason
GC content40 – 60 %Outside range: synthesis failure, poor sequencing
Homopolymer run≤ 4 identical basesLong runs cause polymerase slippage
Hairpin ΔG≥ −2 kcal/molSecondary structure prevents sequencing
Tandem repeatno unit > 8 nt repeated > 3×PCR amplification artefacts
The optimizer does not always clear every violation: on the four example programs, 8 to 60 remain. It also runs before ECC is added, so SYNC, parity and TMR copies are not checked.

Bio Optimizer
Bio Safety · §10

Codon Degeneracy

§ 10.1

The 6-bit codon space has 64 values, but Helix only uses values 0–31 for opcodes and 0–7 for registers. This leaves slack that the optimizer uses to substitute bio-problematic codons with synonymous alternatives that encode the same value but produce better GC content or break homopolymer runs.

Optimization Strategy

§ 10.2
  • GC balancing — slide a window of 20 codons; if GC < 40% swap a low-GC codon for a synonymous high-GC one
  • Homopolymer breaking — detect runs ≥ 4; substitute the 4th codon with a GC-neutral synonym
  • Hairpin avoidance — compute approximate ΔG; if below threshold, reverse-complement the offending region using synonyms where possible
The optimizer rewrites opcode codons to their synonyms (opcodes 0x00 to 0x0F have one each) and reports the violations that remain.

Assembler
Toolchain · §11 — helix-asm

Pipeline

§ 11.1

The assembler transforms .hx source text into a Vec<Codon> through three stages:

  • Parse (helix_asm::parser) — tokenise and produce a SourceProgram with unresolved label refs
  • Resolve (helix_asm::resolver) — compute branch offsets, produce ResolvedProgram
  • Emit (helix_asm::emitter) — encode each Instruction to 4 Codons, return AssemblyOutput

API

§ 11.2
assembler API

// output.codons  : Vec<Codon>  — ready for ECC / VM
// output.labels  : HashMap<String, usize>  — label map
// output.program : ResolvedProgram  — instruction list

Virtual Machine
Toolchain · §12 — helix-vm

Execution Model

§ 12.1

The VM is a simple register machine: 8 × 16-bit registers, a program counter, a flags register (zero, negative), and a small scratch RAM (256 × 16-bit words).

Execution is deterministic and synchronous — no threads, no I/O, no side effects. This makes results reproducible regardless of when or where the DNA is retrieved.

API

§ 12.2
vm usage 
use helix_vm::{Cpu, ProgramLoader};

let prog = ProgramLoader::load(&codons)?;
let mut cpu = Cpu::new();
cpu.execute(&prog)?;

let regs = cpu.registers();
println!("R7 = {}", regs[7]);
println!("R1 = {}", regs[1]);

Simulator
Toolchain · §13 — helix-sim

What is helix-sim?

§ 13.1

helix-sim is a chaos / fault-injection harness. It simulates the DNA storage medium by randomly mutating a DnaSequence according to a configurable error model, decodes it, and counts how many decoded instructions equal the originals. It does not execute the program.

Error Injection Modes

§ 13.2
ModeDescription
SubstitutionRandomly flip a base to another (e.g. A→C). Most common in long-term storage.
DeletionRemove a random base; causes frame shift. Tests SYNC re-framing.
InsertionInsert a random base. Also frame-shifts.
BurstErrorCorrupt a contiguous run of N bases. Tests TMR coverage.

API

§ 13.3
simulator usage 
use helix_sim::{ErrorInjector, InjectionConfig, InjectionMode};

let cfg = InjectionConfig {
    mode: InjectionMode::Substitution,
    rate: 0.01,  // 1% base error rate
    seed: 42,
};
let mutated = ErrorInjector::new(cfg).inject(&dna);
// now decode + execute and compare results
let report: SimReport = run_full_pipeline(&mutated);
Run the simulator over 10,000 trials with rate: 0.001 (0.1%) to get a statistical baseline for your algorithm's error tolerance under realistic DNA storage conditions.

Model Weights
Examples · §15 — archiving neural network weights in DNA

Concept

§ 15.1

Neural network weights are just arrays of floating-point numbers. Helix can archive them by encoding a weight-loader program that reconstructs the weight tensor using IMML/IMMH pairs followed by STORE instructions. At retrieval time, the VM re-materialises the weights into scratch RAM.

For a tiny network (e.g. 128 weights × 16-bit fixed-point), the encoding fits in a single ECC block. For larger networks, multiple blocks are chained.

This is a proof-of-concept for archival, not inference. Execution on the Helix VM is O(n) in weight count — practical only for small models.

Quantisation

§ 15.2

Floating-point weights are quantised to 16-bit unsigned fixed-point (Q8.8 format) before encoding. Each weight w maps to: u16 = clamp(w × 256 + 32768, 0, 65535).
